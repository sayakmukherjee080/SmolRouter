2. Architecture summary

A self-hosted, zero-runtime-dependency OpenAI-compatible AI gateway in one Node.js 22 process. Native http, node:sqlite and fetch replace a web framework, database server and HTTP client. The admin dashboard is a vanilla ES-module SPA served by the same process.

Request path

  1. Browser loads /admin; static assets come from web/.
  2. Admin calls /api/v1/*; session cookie and CSRF header are checked, then the admin API mutates the in-memory registry and SQLite.
  3. Client calls /v1/models or POST /v1/* with a gateway bearer key.
  4. Gateway authenticates, rate-limits, checks budgets and capabilities, selects a route and provider key, then streams the upstream response.
  5. Usage, cost, latency and audit events are batched into SQLite; metrics are kept in memory.

Components

  • Gateway core — routing, failover, key pools, cache-aware pins, cooldowns, probes, response cache.
  • Registry — authoritative in-memory image backed by SQLite, soft deletes and settings.
  • Admin API — 34 endpoints, session/CSRF, CRUD, settings, usage, backups, config transfer.
  • Operations — health/readiness, Prometheus metrics, structured logs, graceful shutdown, daily backups and retention.
  • External surface — only upstream OpenAI-compatible providers. No queue, Redis, Postgres, Docker or cron.
Deployment topology. One Node process, one SQLite file, one dashboard. No container, queue, cache server or cron. Upstream providers are the only external dependency. That is a deliberate simplicity choice and the main reason the operational surface is small.
